# Klasrum — Supabase database foundation (release candidate)

This package is the database foundation for the current Klasrum release. It is designed for a **new, empty Supabase project** and must be run in order.

## Files

1. `001_core_schema.sql` — core multi-school schema, foreign keys, constraints and indexes.
2. `002_security_workflows_views.sql` — JWT authorization helpers, row-level security, SQL grants, controlled score entry, audit history, grade validation, result publication snapshots and read-only broadsheet functions.

Do not run the older `klasrum_secure_schema.sql` or the earlier draft migration package. This package replaces those drafts.

## Important testing status

The files have received a further static security and consistency review. I checked the migration structure, authorization paths, write grants, RLS policies, score workflow, grade-band rules and publication workflow. **They have not been executed against your Supabase project, and no live two-school/two-role penetration test has been performed.** This environment does not have a PostgreSQL/Supabase test instance available. Therefore this is a release-candidate database foundation, not a claim of independently certified or 95–98% security.

Do not run these against a database containing data. Run them first in a fresh Supabase project or a separate staging project, then complete the acceptance tests below before using real student records.

## Installation order

1. Supabase Dashboard → SQL Editor → New query.
2. Paste the complete contents of `001_core_schema.sql` and run it.
3. Confirm that Supabase reports success.
4. Open a separate New query.
5. Paste the complete contents of `002_security_workflows_views.sql` and run it.
6. Confirm success. If either migration returns an error, stop and share the exact error; do not continue to the next step.

Both scripts use transactions. A failed script should roll back its own transaction, but still inspect the SQL Editor result before retrying.

## Identity and provisioning contract

Authorization is based on signed JWT `app_metadata.school_id` and `app_metadata.role`. Never use `user_metadata` for authorization.

The browser must never create or edit profile roles. A trusted server route or Supabase Edge Function using the **service-role key only on the server** must:

1. Verify the requesting user's authority before provisioning anyone.
2. Create the school and Auth user (or invite the user) through Supabase Auth Admin API.
3. Insert the matching `public.profiles` row with the intended school and role.
4. Set the user's `app_metadata` to the matching `school_id` and `role`.
5. Require the user to refresh/sign in again so the JWT contains the new claims.

The service-role key must never appear in SPCK client code, browser JavaScript, GitHub, or a `NEXT_PUBLIC_` environment variable. The publishable key is the only Supabase key intended for browser-side initialization.

## Important database/API contracts for the UI and server

- `public.create_grading_scale(name, ca_max, exam_max, bands, make_default)` — admin-only RPC. Supply all grade bands in one JSON array. Bands must start at 0, be contiguous without gaps/overlaps, and end at `ca_max + exam_max`. This is important because a scale is validated as one complete transaction.
- `public.save_subject_score(student_id, subject_id, term_id, ca_score, exam_score, reason)` — teacher-only RPC. Initial submission may omit a reason; a correction requires a reason. The current assigned teacher can correct a score only while the term is open.
- `public.set_term_status(term_id, status, reason)` — admin-only RPC. Valid transitions are draft→open, open→closed, published→open/closed and closed→open. Reopening a published/closed term requires a reason and marks previous publications as no longer current.
- `public.get_class_broadsheet(class_id, term_id)` — returns the full calculated broadsheet only to the school admin or the exact assigned form teacher. Ties share a rank (`rank()` policy).
- `public.publish_class_result(term_id, class_id)` — admin-only RPC. It refuses publication if any active student is missing a score for any subject assigned to that class. It stores an immutable JSON result snapshot and a SHA-256 hash generated by the database. The optional third legacy parameter is ignored; clients must not supply their own hash.
- `public.verify_result_publication(code)` — public verification metadata, including the snapshot hash, student count and whether the stored snapshot still matches its hash. It does not expose student names or marks publicly.
- Attendance and form-teacher comments are the permitted direct teacher writes, restricted by exact form-teacher class assignment and RLS.

A published snapshot hash verifies the canonical result data stored by Klasrum. It does **not** prove that the original marks were objectively correct, and it is not a hash of the final PDF file bytes. The report service should generate PDFs from the stored snapshot for a published version, not recalculate them from later-edited live data.

## Security boundaries included

- Every school-owned table is scoped by `school_id` and protected with RLS.
- A class row represents one exact class/arm. Teacher access uses class IDs and assignment rows, not class labels.
- Teachers see only assigned class/subject records; form-teacher rights do not grant subject-score rights.
- Admins can manage school configuration and view broadsheets, but authenticated clients have no direct score insert/update/delete privilege.
- Score writes use a controlled RPC; original submitter is preserved, latest editor is recorded, and before/after values plus reason are audited.
- Scores cannot be physically deleted through normal SQL operations. Audit and publication history are protected from update/delete.
- Grade bands and score maxima lock once a scale has been used. Create a new scale for future use.
- Attendance, comments, assignments, profile changes and key class/subject/grading changes are audited.
- Published results are versioned; old versions remain verifiable but are marked not current after reopening/republication.

## Required acceptance tests before onboarding a school

Create two test schools (A and B), at least two classes/arms per school, two teachers with different subject assignments, one form teacher, one admin and sample students. Test using actual signed-in accounts and direct Supabase REST/RPC calls—not only the UI.

1. School A admin cannot read or mutate School B data.
2. A teacher cannot read another school's students, classes, subjects, profiles or scores.
3. A subject teacher can see students in their exact assigned class/arm, but cannot read another class or another subject's scores by direct REST request.
4. A teacher cannot submit or correct marks for an unassigned subject/class.
5. A form teacher can view the full broadsheet only for the assigned class and cannot read or write raw score rows.
6. An admin can manage school configuration and publish results but cannot write raw score rows or calculated values.
7. A correction without a reason fails; a correction with a reason succeeds and creates an audit event preserving the original submitter.
8. A deactivated teacher loses assignment-based access after their JWT is refreshed; test old sessions and force sign-out/session refresh in the app when staff are deactivated.
9. Invalid grade bands (gaps, overlaps, wrong endpoints) fail; a used grading scale cannot have its score maxima or bands changed.
10. Publication fails when any active student-subject score is missing. A successful publication creates a version, code, snapshot and hash. Reopening marks the previous version not current; republishing creates a new version.
11. Verify a valid code, an invalid code and a stored snapshot whose hash no longer matches (in a disposable test database).
12. Attempt direct update/delete of audit rows and score rows; these must fail.

## Not included in this database migration

The schema does not implement the Next.js UI, server-side user provisioning endpoints, parent portal, file storage policies, PDF/Excel renderer, email delivery, backup/restore procedures, or production monitoring. These are application and operations tasks. The database contract is intended to let UI and server development proceed against stable tables, RLS policies and RPCs while the acceptance tests are completed in staging.
